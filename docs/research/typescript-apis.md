# Survey: TypeScript/JS database APIs for DDL, schema, migrations and plans (for smaltts)

Date: 2026-11-06. Method: web search plus prior knowledge of these libraries. Direct page fetches were blocked
in this session (kysely.dev, orm.drizzle.team, dexie.org do not resolve through the session network), so search

Code snippets are illustrative and abbreviated.

## 1. Libraries

### 1.1 Drizzle ORM and drizzle-kit
**Shape.** Tables are TS values built by dialect-specific functions. Types are inferred from the value.
```ts
export const users = pgTable('users', {
  id: serial('id').primaryKey(),
  email: text('email').notNull().unique(),
  orgId: integer('org_id').references(() => orgs.id),
}, (t) => [index('users_org_idx').on(t.orgId)]);
type User = typeof users.$inferSelect;   // InferSelectModel<typeof users>
type NewUser = typeof users.$inferInsert;
```
**DDL representation.** The declared schema is the desired state, and the user writes no DDL statements.
drizzle-kit serializes the TS schema into a JSON snapshot (tables, columns, indexes, FKs, enums...).
- `generate`: diffs the new snapshot against the previous one and writes SQL migration files. On an ambiguous
  change it asks the user whether a rename is meant or a drop plus create.
- `push`: introspects the live DB, diffs it against the schema and applies the changes directly (no files).
- `pull`/`introspect`: DB to generated TS schema file (codegen).
- v1 (beta, 2025-26): the journal is gone. Each migration is a folder `<YYYYMMDDHHmmss>_<name>` holding SQL plus a
  snapshot, and snapshots now carry `prevIds: string[]`, so history is a DAG. `drizzle-kit check` finds
  migrations on separate branches that do not commute. The guide says it moved "from database snapshots to DDL snapshots".
**Typing.** Very strong typing, built on deeply nested conditional generics over the column builder chain.
Runtime-defined tables are possible (`pgTable(name, cols)` with a computed `cols`), but the inferred types
then fall back to wide or `any`-ish types.
**Extensibility.** `customType<{data; driverData}>()` for column types. Dialects are separate module trees
(`pg-core`, `sqlite-core`, `mysql-core`), not plugins.
**Pain points.**
- Rename detection depends on interactive prompts, so CI cannot run it without a human. Renames are sometimes seen as drop plus add.
- Snapshot drift: hand-editing SQL without updating the snapshot leads to wrong diffs later.
- Branch merges conflict on the journal (the v1 DAG is the fix).
- IntelliSense is slow on large schemas (drizzle-orm#800, fixed in 0.28). Dialect-specific builders cannot be reused across dialects.
Sources: https://orm.drizzle.team/docs/drizzle-kit-generate , https://orm.drizzle.team/docs/drizzle-kit-push ,
https://orm.drizzle.team/docs/upgrade-v1 , https://newreleases.io/project/github/drizzle-team/drizzle-orm/release/v1.0.0-beta.16 ,
https://makerkit.dev/docs/tanstack-drizzle/database/migrations ,
https://dev.to/mahdi_benrhouma_fe1c6005/fix-extremely-slow-drizzle-intellisense-on-large-schemas-4nd5

### 1.2 Kysely
**Shape.** A typed query builder over a `Database` interface (written by hand or generated by kysely-codegen).
```ts
await db.schema.createTable('person')
  .addColumn('id', 'integer', (c) => c.primaryKey().autoIncrement())
  .addColumn('name', 'text', (c) => c.notNull())
  .addColumn('org_id', 'integer', (c) => c.references('org.id').onDelete('cascade'))
  .execute();
await db.schema.createIndex('person_name_idx').on('person').column('name').execute();
await db.schema.alterTable('person').addColumn('age', 'integer').execute();
```
**DDL representation.** The schema builder is untyped: table and column names are strings and is not checked
against `DB`. Every builder, schema builders included, builds an immutable **OperationNode tree**
(`CreateTableNode`, `ColumnDefinitionNode`, `AlterTableNode`, `SelectQueryNode`...). A dialect `QueryCompiler`
then walks the tree into SQL text. `.toOperationNode()` and `.compile()` expose the tree and the SQL (from memory).
**Migrations.** `Migrator` with `FileMigrationProvider`. It keeps an operation log: ordered `up/down(db)` functions
are tracked in a `kysely_migration` table with a lock table. There is no diffing and no snapshots. Migrations
should take `Kysely<any>` because the schema at migration time differs from today's types.
**Plugins.** `KyselyPlugin { transformQuery(args: {node, queryId}): RootOperationNode; transformResult(args) }`.
Plugins usually subclass `OperationNodeTransformer`. They run in registration order for queries and in reverse
for results. A plugin can be applied to a single query with `withPlugin`. Docs advise a `WeakMap` keyed by `queryId` for state.
Built-in plugins: CamelCase, WithSchema (rewrites every table ref to a schema), ParseJSONResults, DeduplicateJoins.
**Typing.** It types queries but not DDL. `$assertType` is the escape hatch for TS2589 "excessively deep".
`sql\`...\`` is the raw escape hatch, with `sql.ref/sql.id/sql.lit`.
**Lesson.** The cleanest reference for "builder, then data tree, then backend" in TS. Plugins rewrite the data tree
rather than strings. It is weak exactly where smaltts needs strength: DDL is stringly typed and not
linked to the types.
Sources: https://kysely-org.github.io/kysely-apidoc/interfaces/KyselyPlugin.html ,
https://www.mintlify.com/kysely-org/kysely/api/plugins/custom-plugins , https://kysely.dev/docs/recipes/excessively-deep-types ,
https://kysely.dev/docs/migrations (from memory), https://github.com/RobinBlomberg/kysely-codegen (from memory)

### 1.3 Prisma
**Shape.** A separate DSL (PSL) in `schema.prisma`, plus a generated client.
```prisma
model User { id Int @id @default(autoincrement())  email String @unique  posts Post[]  @@index([email]) }
```
**DDL representation.** Desired state lives in PSL. The Rust schema engine diffs one of datamodel,
migrations dir, live DB or empty against another and emits SQL.
- `migrate dev` writes SQL files and needs a shadow DB to replay the history.
- `db push` skips history.
- `db pull` introspects into PSL.
- `migrate diff --from-X --to-Y --script` is a general diff tool. In v7 the URL flags moved to `--from/to-config-datasource`.
**DMMF** (Data Model Meta Format) is the internal JSON description of the schema used by generators. It is
"public in practice, unstable in theory" (from memory).
**Query side.** v6.7+ / v7 replaced the Rust query engine with a TS/WASM **Query Compiler**. A client query is compiled
to an internal **query plan**, and the plan is interpreted in JS over a driver adapter. This shows that
"plan as data, small interpreter" beats "opaque engine binary" on bundle size (14MB to 1.6MB) and on avoiding
serialization between JS and the engine.
**Pain points.**
- A separate language and codegen step: types are stale until `prisma generate` runs.
- Cannot define schema at runtime at all.
- Limited control over the DDL that gets emitted (partial indexes and views came late, through "preview features").
- Shadow DB requirement. Opaque engine (historically).
Sources: https://www.prisma.io/docs/cli/v7/migrate/diff , https://www.prisma.io/docs/orm/prisma-migrate/workflows/generating-down-migrations ,
https://www.prisma.io/blog/rust-to-typescript-update-boosting-prisma-orm-performance , https://www.prisma.io/docs/v6/orm/more/internals/engines

### 1.4 TypeORM
**Shape.** Decorated entity classes (`@Entity() class User { @PrimaryGeneratedColumn() id; @Column() name }`).
**DDL object model (worth studying).** `QueryRunner` has an imperative schema API over plain metadata objects:
```ts
await queryRunner.createTable(new Table({ name: 'question', columns: [
  { name: 'id', type: 'int', isPrimary: true }, { name: 'name', type: 'varchar' }] }), true);
await queryRunner.createIndex('question', new TableIndex({ name: 'IDX_Q_NAME', columnNames: ['name'] }));
await queryRunner.addColumn('answer', new TableColumn({ name: 'questionId', type: 'int' }));
await queryRunner.createForeignKey('answer', new TableForeignKey({ columnNames: ['questionId'],
  referencedTableName: 'question', referencedColumnNames: ['id'], onDelete: 'CASCADE' }));
```
Also `getTable()` / `getTables()` (introspection into the same `Table` objects), `hasTable`, `renameColumn`, `changeColumn`.
`createTable(table, ifNotExists?, createForeignKeys?, createIndices?)`.
**Migrations.** `migration:generate` diffs entity metadata against the live DB, using the same `Table` objects, and emits
QueryRunner/SQL `up/down` code. `synchronize: true` is the push mode.
**Pain points.**
- Decorators (the legacy `experimentalDecorators` plus `emitDecoratorMetadata`) do not fit the TC39 decorators standard.
- Metadata is global and registered as a side effect.
- Generated migrations that drop and recreate columns. Weak types (entities are classes, so nullability lies).
- `synchronize` destroys data in production. Low maintenance for a long time.
**Good part.** `Table` / `TableColumn` / `TableIndex` are a plain, symmetric DDL object model shared by introspection,
diff and execution. The weak part: they are mutable classes with dialect strings for types, and many fields are optional.
Sources: https://typeorm.io/docs/migrations/api , https://cdn.jsdelivr.net/npm/typeorm@0.3.29/query-runner/QueryRunner.d.ts

### 1.5 MikroORM
Entities through decorators, `defineEntity`, or the `EntitySchema` object (no decorators).
`EntitySchema` is a schema-as-value option. `MetadataStorage` and `EntityMetadata` are the central model.
`SchemaGenerator` (`createSchema`, `updateSchema`, `getUpdateSchemaSQL`, `dropSchema`) diffs metadata against
`DatabaseSchema.create(...)` (an introspected model of `DatabaseTable` / `Column` / `Index`) through a `SchemaComparator`.
The output is a structured `SchemaDifference`, which is turned into SQL afterwards. Migrations store a **snapshot JSON** of
the schema to avoid introspecting the DB (from memory). It now ships a Kysely integration (`MikroKyselyPlugin`), which
shows ORMs moving onto Kysely's node tree.
**Lesson.** Separating the introspected model, the comparator, a typed diff and the SQL emission is the right
layering. The diff is a first-class value that can be inspected and filtered before it is applied.
Sources: https://mikro-orm.io/docs/schema-generator (from memory), https://mikro-orm.io/api/sql/class/MikroKyselyPlugin

### 1.6 Knex / Sequelize / Objection
- **Knex** `knex.schema.createTable('t', (t) => { t.increments(); t.string('name').notNullable().index(); })`. It uses a
  callback mutation builder and compiles straight to SQL strings (`.toSQL()`). There is no intermediate tree. Migrations are an
  operation log (`up/down` plus a `knex_migrations` table). `alterTable` with `.alter()` is fragile on SQLite (table rebuild).
  Untyped. Kysely's design was a reaction to this.
- **Sequelize** `queryInterface.createTable(name, attrs)`, `addColumn`, `addIndex`, `describeTable`. A plain-object
  attribute map (`{ type: DataTypes.STRING, allowNull: false }`). Untyped, with an operation log (umzug). `sync({alter})` is risky.
- **Objection** uses Knex for DDL. Only the model layer is added.
Sources: https://knexjs.org/guide/schema-builder.html , https://sequelize.org/docs/v6/other-topics/query-interface/ (from memory)

### 1.7 Zapatos / pgtyped / kysely-codegen (DB first, then types)
Zapatos introspects Postgres and generates `schema.d.ts`, with per-table `Selectable/Insertable/Updatable/Whereable`
types. Queries use tagged templates with typed `self/cols/vals`. Typing comes from codegen, not inference. It is the
"discovered schema" route, and it works only when discovery happens at build time.
Source: https://jawj.github.io/zapatos/ (from memory)

### 1.8 Atlas (and its TS/Drizzle integrations), pg-mig
Atlas is Terraform for schemas. It loads the desired state (HCL, SQL, or an ORM through an external loader such as Drizzle)
into a dev DB, introspects both sides, diffs them and produces a **plan**. It also runs lint/analysis of the plan:
destructive changes, table locks, data-dependent changes. A versioned mode with `atlas.sum` integrity is also available.
Known limitation: changes that cannot be inferred from state, such as renames and type narrowing, need hints.
**Lesson.** Desired state is good for authoring. Running it needs (a) explicit rename/intent hints, (b) a diff that can be
reviewed and linted, and (c) a versioned log for production.
Sources: https://atlasgo.io/declarative/apply , https://atlasgo.io/tags/drizzle-orm , https://github.com/ariga/atlas/discussions/3582

### 1.9 Effect SQL / @effect/schema, Zod-driven tables
- `Model.Class<Group>('Group')({ id: Model.Generated(GroupId), name: Schema.NonEmptyTrimmedString, ... })` is one
  schema value that produces variants (`select`, `insert`, `update`, `json`...). Schema values are also runtime
  codecs (decode/encode), and they are introspectable ASTs (`Schema.ast`). It does not generate DDL.
- Zod-driven tables: drizzle-zod / drizzle-typebox derive validators *from* tables. The opposite direction (Zod, then table)
  exists in small libraries. The key concept is the same either way: **a schema value is both data you can walk at runtime and a
  type source at compile time.**
Sources: https://effect-ts.github.io/effect/sql/Model.ts.html , https://orm.drizzle.team/docs/zod (from memory)

### 1.10 Browser / embedded engines
- **IndexedDB** is DDL-first by design. Schema changes (`createObjectStore`, `createIndex`, `deleteObjectStore`) are
  allowed *only* inside the `versionchange` transaction of `open(name, version)` → `onupgradeneeded(e: {oldVersion,
  newVersion})`. Upgrades are atomic. Other tabs receive `onversionchange` and must close, or the upgrade is `blocked`.
  The schema is an integer version plus imperative steps. There is no typing (idb by Jake Archibald adds a typed `DBSchema`
  interface).
- **Dexie**: `db.version(2).stores({ friends: '++id, name, &email, *tags, [first+last]' })` plus `.upgrade(tx => ...)`.
  It is a compact, stringly-typed DSL (`++` auto-inc, `&` unique, `*` multi-entry, `[a+b]` compound). Dexie 3+ diffs
  declared versions, so only versions that have upgrade functions need to be kept (from memory). Typing comes from
  `EntityTable<T,'id'>` declarations, not from the schema string. The string DSL is concise but cannot be checked.
- **RxDB**: JSON-Schema-based `RxJsonSchema<DocType>` with `version` plus `migrationStrategies: {1: oldDoc => newDoc}`.
  Types come from `ExtractDocumentTypeFromTypedRxJsonSchema<typeof schema>` with `as const`. It is the clearest example of
  a "runtime JSON schema → type" pattern, and of a migration step per version as plain functions.
- **TinyBase**: `createStore().setTablesSchema({pets: {species: {type:'string'}, sold: {type:'boolean', default:false}}} as const)`
  returns a **re-typed store** (import from `tinybase/with-schemas`). Types change only because the method returns a
  new type. This pattern is "methods that return a narrower type".
- **DuckDB-WASM**: `db.registerFileHandle/registerFileURL/registerFileBuffer` (on the DB) then `conn.query(sql)` /
  `conn.insertArrowTable(table, {name})` / `insertCSVFromPath` (on the connection). Arrow is the data interchange.
  Pain point: the apache-arrow major version must match, or inserts fail silently. No typed API: SQL strings in, Arrow out.
  It does have `getTableNames(sql)` and the JSON-serialized plans of extensions (from memory).
- **PGlite / ElectricSQL**: Postgres in WASM. The API is `pg.query(sql, params)` / `exec`, plus live queries and extensions
  passed as `{ extensions: { vector, live } }`. Extensions are objects with a `setup` hook, which is a good plugin shape.
  DDL is through SQL strings. ORMs (Drizzle) layer on top.
- **Substrait in JS**: `substrait-js` has TS typings plus a parser/visualizer and is stale (last push in 2023). There is no maintained TS
  plan **builder**. Java has `substrait-java`'s builder. Apache Arrow JS / DataFusion have no relational-plan builder in TS
  either. **This is a gap smaltts can fill.**
Sources: https://developer.mozilla.org/en-US/docs/Web/API/IDBOpenDBRequest/upgradeneeded_event (from memory),
https://dexie.org/docs/Tutorial/Design#database-versioning (from memory), https://rxdb.info/rx-schema.html (from memory),
https://tinybase.org/guides/schemas-and-persistence/schema-based-typing/ , https://duckdb.org/docs/stable/clients/wasm/data_ingestion ,
https://pglite.dev/docs/api (from memory), https://awesome.ecosyste.ms/projects/github.com%2Fsubstrait-io%2Fsubstrait-js

## 2. Cross-cutting patterns

| Concern | Patterns seen | Verdict for smaltts |
|---|---|---|
| DDL form | SQL strings (Knex, DuckDB), node tree (Kysely), object model (TypeORM Table, MikroORM DatabaseTable), DSL (PSL, Dexie strings) | **Plain data object model** = the plan data itself |
| Migration model | operation log (Knex, Kysely, IndexedDB, RxDB) vs desired state + diff (drizzle push, Prisma, Atlas, MikroORM) | **Both**: desired state is diffed into an op list. The op list is reviewable data, and the log stores op lists |
| Diff state | introspect live DB (push, Atlas) vs snapshot JSON (drizzle generate, MikroORM) | Introspect the engine (it is local and cheap). Snapshots are optional |
| Rename ambiguity | interactive prompts (drizzle), hints (Atlas), stable IDs | Explicit `renamedFrom` / stable ids; never prompt |
| Typing | inference from value (Drizzle, TinyBase, RxDB `as const`), codegen (Prisma, Zapatos, kysely-codegen), hand-written interface (Kysely, idb) | Inference from value plus an explicit untyped tier |
| Extensibility | node-tree transformers (Kysely), dialect modules (Drizzle), extension objects (PGlite) | Plan transformers plus plugin descriptors as data |

## 3. Lessons for smaltts (opinionated)

1. **The DDL API is a constructor of plan data, not a statement runner.** `createTable(...)` returns a plain, JSON-serializable,
   frozen op value that maps 1:1 to the engine's language-neutral plan. Executing it is a separate step (`db.apply(ops)`).
   Every op can be built, printed, diffed, stored and sent without a connection. This is Kysely's
   OperationNode idea, but the nodes *are* the public format rather than an internal detail.
2. **One schema model for declare, introspect, diff and apply.** The model has the shape of TypeORM's `Table` / MikroORM's `DatabaseTable`, but is
   immutable data. `db.catalog()` returns the same `TableDef` values that users declare. `diff(from, to)` returns
   `Op[]` (createTable / alterTable{addColumn, dropColumn, renameColumn...} / createIndex / drop...). There is no second "DDL AST".
3. **Desired state and the op log are both first-class.** Provide `plan = diff(current, desired)` and `apply(plan)`, plus a versioned
   log (`migrations: [{id, ops}]`) with an integrity hash. Store **op lists**, not SQL. Allow `diff` to be filtered and linted
   (destructive / rewrite / lossy cast flags on each op, as in Atlas).
4. **Never prompt for renames.** Columns and tables can carry `renamedFrom: 'old'` (or a stable `id`). A plain diff never produces a rename, and
   reports "drop + add" as destructive so a policy can reject it. This avoids drizzle's interactive prompts.
5. **Two typing tiers, same runtime values.**
   - Static tier: `const t = table('users', { id: int64().primaryKey(), email: utf8().notNull() })`. Columns are
     *values* whose generic params carry the type. `Infer<typeof t>` / `InferInsert`. Use `const` type parameters
     (TS 5.0) so users do not need `as const`.
   - Dynamic tier: `tableFromSchema(name, discoveredCols: ColumnDef[])` returns `TableDef<Row = Record<string, Value>>`.
     The *same* runtime type is used. An optional `assertShape(def, staticDef)` / `def.as<T>()` narrows after a runtime check (as with Effect/Zod decoding).
   Both tiers must produce identical plan data. The dynamic tier must not feel like an `any` escape hatch: give it
   runtime validation and good error messages.
6. **Keep type-level computation shallow.** Large ETL schemas (hundreds of columns) kill deep conditional types (drizzle#800,
   Kysely TS2589). Map column type tags to TS types through a flat lookup interface (`TypeMap[tag]`). Avoid recursive builder
   chains that accumulate state in generics. Use object-literal options (`int64({ nullable: false })`) instead
   of long `.notNull().default().unique()` chains where the chain would have to change the type.
7. **Types are engine type tags, not dialect strings.** Use a closed union of logical types (Arrow-like: int32, int64, float64, utf8,
   binary, bool, date32, timestamp(unit,tz), decimal(p,s), list(T), struct{...}) as data. Do not use free-form `'varchar(255)'` strings
   (the problem in TypeORM, Knex and Kysely's schema builder). Arrow alignment helps ETL users (DuckDB-WASM shows the version-mismatch trap,
   so keep an engine-owned type model and convert at the edges).
8. **Introspection is the plan language too.** Catalog reads return the same defs, so "copy schema from source X, add
   index, create" is `createTable({...srcDef, name})` plus `createIndex`. Make defs easy to transform with spreads and helpers
   (`withColumn`, `withoutColumn`, `renameColumn`) that return new values.
9. **Extensibility through plan transformers and plugin descriptors.** Plugins are data descriptors (name, version, methods with
   typed signatures) and optional TS-side helpers. Plan rewriting is Kysely-style: `transform(plan) => plan` with a visitor
   over the positional operator tree. Keep the visitor generic over node kinds so unknown or plugin nodes pass through.
10. **Learn from IndexedDB's upgrade model.** Atomic schema transactions (all ops in a plan apply or none do), a monotonic
    schema version or hash on the database, and a defined story for other connections or tabs during an upgrade.
    Dexie and RxDB show that per-version upgrade callbacks plus declared versions are workable. smaltts can do
    better with op lists plus data-transform plans.
11. **Positional operator trees need a naming layer in TS.** The engine is positional. The TS builder should resolve column names
    to ordinals at build time against the input's schema (and fail early), and keep names only as metadata.
    Expose `explain(plan)` / pretty-printer output. Never hide the plan (unlike Prisma's historical opaque engine; Prisma itself
    moved to "compile to a plan, interpret in JS").

### Patterns to avoid
- **Decorator entities and global metadata registries** (TypeORM, legacy MikroORM): side effects, legacy-decorator lock-in, cannot be built
  at runtime.
- **Stringly-typed DDL**: column types as SQL strings (Knex/Kysely/TypeORM), Dexie-style mini-DSLs inside strings,
  unchecked `'table.column'` reference strings. Use typed references (`t.cols.id`) and value-level type tags.
- **A separate schema language plus codegen as the only typed path** (Prisma PSL): bad for runtime-discovered schemas. Codegen can be
  an optional extra (`smaltts gen` from a catalog), never required.
- **ORM layers that hide the plan** or produce queries the user cannot inspect. Also avoid `synchronize: true`-style automatic
  application of diffs without review.
- **Interactive or CLI-only diffing** (drizzle prompts). The diff must be a library function that returns data.
- **Dialect-forked builder trees** (drizzle's pg-core/sqlite-core): one engine means one builder.
- **Mutable callback builders** (`createTable('t', t => { t.string(...) })`): hard to type, compose or serialize.

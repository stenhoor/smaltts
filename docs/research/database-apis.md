# Programmatic (beyond-SQL-text) database APIs: survey and lessons for smaltts

Scope: how databases and adjacent tools expose DDL, catalog introspection, plans/costs, extensions and bulk-load paths as APIs and data rather than SQL strings. Written for smaltts (TypeScript, DDL-first, plan-first API over smaltdb, an embedded browser engine whose input is language-neutral plan data).

Method note: written mostly from the vendors' reference documentation (URLs below), with spot checks by web search. Some hosts (for example substrait.io) were not reachable from this session, so the Substrait DDL/Write details were checked against the generated protobuf bindings (docs.rs) and the spec PRs. Substrait's DDL/Write messages are still changing, so pin a proto version.

---

## 1. SQLite

**Object model:** Statements, not objects. The only "schema object" API is the text in `sqlite_schema` (the original CREATE statements, stored verbatim) plus introspection functions.

- **Core C API:** `sqlite3_prepare_v2` / `step` / `column_*`; statement metadata (`sqlite3_column_table_name`, `sqlite3_column_origin_name`, `sqlite3_column_decltype`). `sqlite3_table_column_metadata()` returns declared type, collation, NOT NULL, PK and autoincrement for one column. https://sqlite.org/c3ref/table_column_metadata.html
- **Schema as table-valued pragma functions:** `pragma_table_info`, `pragma_table_xinfo`, `pragma_index_list`, `pragma_index_xinfo`, `pragma_foreign_key_list`, so the catalog can be queried relationally (`SELECT * FROM pragma_table_info('t')`). https://sqlite.org/pragma.html#pragfunc
- **DDL:** Text only. `ALTER TABLE` is very limited (rename table or column, add or drop column). The documented 12-step "create new table, copy, drop, rename" procedure is the general way to make an arbitrary change, and every ORM migration tool (Django, Alembic batch mode, Prisma, Drizzle) generates that rebuild. https://sqlite.org/lang_altertable.html#otheralter
- **Virtual table module API:** `sqlite3_create_module` registers an `sqlite3_module` vtable (xCreate/xConnect/xBestIndex/xFilter/xNext/xColumn/xUpdate...). The schema is declared by passing a CREATE TABLE *string* to `sqlite3_declare_vtab`. `xBestIndex` is a small planner negotiation: the engine offers constraints, ORDER BY and LIMIT, and the module returns an index number, an estimated cost, estimated rows and which constraints it consumes. This is the model for "external tables with pushdown." https://sqlite.org/vtab.html
- **Session extension:** `sqlite3session_*` records changes to attached tables. Changesets/patchsets are binary blobs that you can apply (`sqlite3changeset_apply` with a conflict handler), invert and concatenate. This gives logical change data capture (CDC) and sync as data. https://sqlite.org/sessionintro.html
- **Backup API:** `sqlite3_backup_init/step/finish` makes an incremental online page copy. https://sqlite.org/backup.html
- **Plans:** `EXPLAIN QUERY PLAN` returns rows (id, parent, detail), so the plan is a tree but has no costs. `EXPLAIN` returns VDBE bytecode. `sqlite3_stmt_scanstatus` gives per-loop estimates and actuals. https://sqlite.org/eqp.html
- **ORMs:** They keep their own model (Drizzle/Prisma schema), diff it against `pragma_*` introspection, and emit SQL text. The engine never sees a structured DDL object.

**Lesson:** Storing DDL as the original text and parsing it back is the anti-pattern smaltts should avoid. Two parts are worth copying: xBestIndex's cost negotiation for external tables, and changesets as a portable change format.

## 2. PostgreSQL

**Object model:** Statements over the wire. Internally, every DDL statement is a parse node (`CreateStmt`, `AlterTableStmt` with `AlterTableCmd` subcommands). The catalog (`pg_catalog`: `pg_class`, `pg_attribute`, `pg_index`, `pg_constraint`, `pg_depend`, ...) is the source of truth, and it is relational and OID-keyed. https://www.postgresql.org/docs/current/catalogs.html
- **DDL generation from the catalog:** `pg_get_indexdef`, `pg_get_viewdef`, `pg_get_constraintdef`, `pg_get_functiondef`, `pg_get_triggerdef`. There is no `pg_get_tabledef`; pg_dump assembles table DDL itself. https://www.postgresql.org/docs/current/functions-info.html
- **pg_depend** records object dependencies. Drop RESTRICT/CASCADE and migration ordering both rely on it.
- **libpq:** connection, `PQexecParams`, `PQprepare`, pipeline mode, COPY sub-protocol (`PQputCopyData`/`PQgetCopyData`). https://www.postgresql.org/docs/current/libpq.html
- **COPY protocol:** the bulk-load path (text, CSV or binary), streamed with no per-row statement overhead. https://www.postgresql.org/docs/current/sql-copy.html
- **SPI:** an in-server C API for running queries inside functions (`SPI_execute`, `SPI_prepare`, `SPI_cursor_open`). It is still SQL-text based. https://www.postgresql.org/docs/current/spi.html
- **Event triggers:** fire on `ddl_command_start/end`, `sql_drop` and `table_rewrite`. `pg_event_trigger_ddl_commands()` returns object identity, command tag and the internal parse tree (`pg_ddl_command`), which is how DDL auditing and replication tools work. `table_rewrite` exposes whether an ALTER will rewrite the table. https://www.postgresql.org/docs/current/event-triggers.html
- **Planner hooks and the Custom Scan API:** `planner_hook`, `set_rel_pathlist_hook`, `set_join_pathlist_hook`. CustomScan providers add `CustomPath` nodes with costs, so plugins compete inside the optimizer. https://www.postgresql.org/docs/current/custom-scan.html
- **FDW API:** `GetForeignRelSize`, `GetForeignPaths`, `GetForeignPlan`, `BeginForeignScan`/`IterateForeignScan`, modify callbacks, `ImportForeignSchema`. Objects are modeled as SERVER, USER MAPPING and FOREIGN TABLE, which is a clean separation of connection, credentials and table. https://www.postgresql.org/docs/current/fdwhandler.html
- **Logical replication / logical decoding:** output plugins (pgoutput, wal2json) stream row-level changes. https://www.postgresql.org/docs/current/protocol-logical-replication.html
- **libpg_query / pg_query:** Postgres's real parser extracted as a library. It turns SQL into a JSON or protobuf parse tree and deparses back (`pg_query.deparse`), so DDL can be treated as data in any language. https://github.com/pganalyze/libpg_query
- **EXPLAIN (FORMAT JSON, ANALYZE, BUFFERS, VERBOSE, SETTINGS, GENERIC_PLAN):** a nested plan tree with `Startup Cost`, `Total Cost`, `Plan Rows`, `Plan Width`, and actuals under ANALYZE. Tools like explain.dalibo.com consume it. https://www.postgresql.org/docs/current/sql-explain.html
- **Extensions:** `CREATE EXTENSION` with versioned upgrade scripts (`ext--1.0--1.1.sql`) and `pg_extension` membership via pg_depend.

**Lesson:** Postgres shows the value of a single parse-node schema for DDL (libpg_query proves the community wants it as JSON), a dependency graph, an explicit server/mapping/table split for external data, cost-carrying plan JSON, and plugins that join the optimizer through costed paths.

## 3. Oracle

The most complete "DDL as data" toolbox of any vendor.
- **DBMS_METADATA:** `GET_DDL(object_type, name, schema)` generates DDL from the dictionary. `OPEN/SET_FILTER/SET_TRANSFORM_PARAM/FETCH_CLOB` works as a programmatic browse API, with transform parameters such as STORAGE=false, SEGMENT_ATTRIBUTES=false and SQLTERMINATOR. The XML and **SXML** formats are a simplified, normalized XML document per object, intended for comparison. `CONVERT` turns SXML into DDL. https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_METADATA.html
- **DBMS_METADATA_DIFF:** `COMPARE_SXML` / `COMPARE_ALTER` / `COMPARE_ALTER_XML` take two object versions and return the difference as SXML, as ALTER statements, or as an ALTER_XML document. Each ALTER in ALTER_XML is annotated with whether it is safe or lossy and with the parsed items (column names and so on). This is a first-class diff-to-migration-plan facility. https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_METADATA_DIFF.html
- **DBMS_SQL:** low-level dynamic SQL (parse, bind, define columns, describe columns), giving result-shape metadata before execution. https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_SQL.html
- **DBMS_REDEFINITION:** online table reorganization. The steps are `CAN_REDEF_TABLE` (precheck), `START_REDEF_TABLE` (interim table plus materialized-view-log sync), `COPY_TABLE_DEPENDENTS`, `SYNC_INTERIM_TABLE`, `FINISH_REDEF_TABLE` (brief lock and swap) and `ABORT_REDEF_TABLE`. The multi-step, resumable, abortable change plan is explicit in the API. https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_REDEFINITION.html
- **Edition-based redefinition (EBR):** multiple versions of code and views coexist ("editions"), with editioning views and cross-edition triggers for zero-downtime application upgrades. https://docs.oracle.com/en/database/oracle/oracle-database/19/adfns/editions.html
- **DBMS_STATS:** gather, export, import, lock and set statistics (`SET_TABLE_STATS`, `EXPORT_SCHEMA_STATS` into a stat table). Statistics are data that can be moved between environments so plans are reproducible. https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_STATS.html
- **DBMS_XPLAN:** `DISPLAY`, `DISPLAY_CURSOR` (actual plan with runtime stats), `DISPLAY_SQL_PLAN_BASELINE`. PLAN_TABLE stores rows of id/parent_id/operation/cost/cardinality/bytes. https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_XPLAN.html
- **SQL Plan Management (DBMS_SPM):** plan baselines are captured, evolved and accepted. New plans are verified before they are used, so plans can be pinned, stored and reviewed. https://docs.oracle.com/en/database/oracle/oracle-database/19/tgsql/overview-of-sql-plan-management.html
- **DBMS_DATAPUMP:** a job-based export and import API (`OPEN`, `ADD_FILE`, `METADATA_FILTER`, `METADATA_REMAP`, `DATA_FILTER`, `START_JOB`, `GET_STATUS`) that can attach to and detach from running jobs. Remaps (schema and tablespace) are declarative transforms on metadata. https://docs.oracle.com/en/database/oracle/oracle-database/19/arpls/DBMS_DATAPUMP.html

**Lesson:** Oracle combines a normalized comparison format (SXML), diff output as both statements and structured XML with safety annotations, prechecks (CAN_REDEF), long-running DDL as a stateful job, and statistics and plans that can be exported and pinned.

## 4. MySQL

- **X DevAPI** (Connector/Node.js, Python, Java, mysqlsh): a fluent CRUD API. The calls are `session.getSchema()`, `schema.createCollection()`, `collection.add/find/modify/remove().where().bind().execute()`, and for tables `table.select().where().orderBy()`, `table.insert()`, `.update()`. Collections are JSON document tables with `createIndex(name, {fields:[...]})`. Statements are built as objects and sent as protobuf messages (X Protocol Mysqlx.Crud.Find and so on), not text, but relational DDL is still mostly `session.sql()`. https://dev.mysql.com/doc/x-devapi-userguide/en/
- **information_schema** (SQL-standard catalog views) plus `SHOW CREATE TABLE`, which is DDL generation from the catalog. Since MySQL 8 the catalog is a transactional data dictionary. https://dev.mysql.com/doc/refman/8.0/en/information-schema.html
- **Online DDL:** `ALGORITHM=INSTANT|INPLACE|COPY` and `LOCK=NONE|SHARED|EXCLUSIVE` are clauses. If you request a level the operation cannot meet, the statement errors instead of silently falling back. The manual's per-operation table records whether each operation is instant, in place, rebuilds the table, permits concurrent DML, or only changes metadata. That classification is a contract that callers can rely on. https://dev.mysql.com/doc/refman/8.0/en/innodb-online-ddl-operations.html
- **gh-ost and pt-online-schema-change:** external online-DDL tools. pt-osc uses triggers plus a shadow table and chunked copy. gh-ost uses a shadow table, reads the binlog, throttles, can be paused through a socket, and has a postponable cut-over. Both add `--dry-run` and `--execute` modes. A schema change becomes a migration job with progress, throttling and an operator-controlled cut-over. https://github.com/github/gh-ost , https://docs.percona.com/percona-toolkit/pt-online-schema-change.html
- **EXPLAIN FORMAT=JSON / TREE, EXPLAIN ANALYZE:** costs (`query_cost`, `read_cost`, `eval_cost`) and estimated rows. https://dev.mysql.com/doc/refman/8.0/en/explain.html

**Lesson:** Classify every alter operation (instant, metadata-only, rewrite, blocking), let callers assert the class they require, and fail rather than degrade. Treat a long change as a job.

## 5. SQL Server

- **SMO (SQL Server Management Objects):** a true object model. `Server > Databases > Database > Tables > Table > Columns/Indexes/ForeignKeys/Checks/Triggers`. You construct a `new Table(db, "T")`, add `new Column(t, "c", DataType.Int)` and call `t.Create()`. You can mutate properties and then call `t.Alter()`, or call `Drop()`. `Script(ScriptingOptions)` produces DDL from any object. `Scripter` with `DependencyWalker` orders scripts by dependency. `ServerConnection.SqlExecutionModes = CaptureSql` records the DDL that SMO *would* run without executing it, which is plan-before-apply built into the object model. https://learn.microsoft.com/en-us/sql/relational-databases/server-management-objects-smo/overview-smo
- **DacFx:** a declarative model of a whole database (`TSqlModel`) built from .sql files or extracted from a live DB, packaged as a **.dacpac**. `DacServices.GenerateDeployScript` / `GenerateDeployReport` / `Publish` diff the model against the target and emit a deploy script plus an XML deploy report with operations and **alerts** (DataIssue for possible data loss, and so on). Options such as `BlockOnPossibleDataLoss`, `DropObjectsNotInSource` and `IgnoreColumnOrder` control behaviour. Refactor logs record renames so a rename is not treated as a drop plus create. Static code analysis rules run over the model. https://learn.microsoft.com/en-us/sql/tools/sql-database-projects/concepts/data-tier-applications/overview , https://learn.microsoft.com/en-us/dotnet/api/microsoft.sqlserver.dac.dacservices
- **Showplan XML:** `SET SHOWPLAN_XML ON`, `SET STATISTICS XML ON`. A published XSD defines RelOp nodes with EstimateRows, EstimatedTotalSubtreeCost, EstimateIO and EstimateCPU, and Query Store persists plans. https://learn.microsoft.com/en-us/sql/relational-databases/performance/display-and-save-execution-plans , schema: http://schemas.microsoft.com/sqlserver/2004/07/showplan
- **Bulk:** `SqlBulkCopy` and the TDS bulk-load stream.

**Lesson:** SMO and DacFx are the closest precedent for smaltts. SMO is the imperative object graph with `Script()` and capture mode. DacFx is the declarative desired-state model with diff, a deploy report, data-loss alerts, rename tracking via a refactor log, and lint.

## 6. DuckDB

- **Relational API:** In Python, `duckdb.table('t')`, `.filter()`, `.project()`, `.aggregate()`, `.join()`, `.order()`, `.limit()`, `.union()`. Relations are lazy and composable, `.explain()` and `.sql_query()` show the plan and SQL, and `.create('t')`, `.insert_into('t')` and `.to_parquet()` are sinks. The C++ `Relation` class is the same idea. https://duckdb.org/docs/stable/clients/python/relational_api
- **Appender API** (C, C++, Java, Go, and others): a row or column (DataChunk) bulk-insert path that bypasses SQL. https://duckdb.org/docs/stable/data/appender
- **Catalog:** `duckdb_tables()`, `duckdb_columns()`, `duckdb_indexes()`, `duckdb_constraints()`, `duckdb_views()`, `duckdb_dependencies()`, `duckdb_functions()` and `duckdb_extensions()` are table functions. Each row includes a `sql` column that regenerates the DDL. https://duckdb.org/docs/stable/sql/meta/duckdb_table_functions
- **Substrait:** `get_substrait`, `get_substrait_json` and `from_substrait` (now a community extension maintained by substrait-io and marked experimental). https://duckdb.org/community_extensions/extensions/substrait.html
- **EXPLAIN (FORMAT JSON) / EXPLAIN ANALYZE**, plus profiling output as JSON with per-operator timing and cardinality. https://duckdb.org/docs/stable/dev/profiling
- **Extensions:** a C extension API (stable ABI) for registering scalar, aggregate and table functions, types, replacement scans, storage extensions (`ATTACH 'x' (TYPE postgres)` for external catalogs), optimizer extensions, and parser extensions. `INSTALL`/`LOAD` with signed extensions. https://duckdb.org/docs/stable/extensions/overview , storage: `ATTACH` and secrets via `CREATE SECRET`. DuckDB-Wasm runs in the browser and is the closest embedded-browser precedent.

**Lesson:** Use lazy relation objects that can explain themselves and render to SQL or a plan. Make the appender a first-class bulk path. Expose the catalog through functions that include regenerated DDL. ATTACH plus SECRET separates connections and credentials from tables.

## 7. Apache Calcite, Substrait, DataFusion, Spark/Delta

- **Calcite RelBuilder:** a stack-based builder (`builder.scan("EMP").filter(builder.equals(builder.field("DEPTNO"), builder.literal(10))).aggregate(builder.groupKey("DEPTNO"), builder.count(false, "C")).build()`) that produces `RelNode` trees. It does light simplification while building, `RelOptUtil.toString` / `RelJsonWriter` serialize the tree, and `RelToSqlConverter` emits SQL for any dialect. Schema SPI: `Schema`, `Table`, `ScannableTable`, `FilterableTable`, `TranslatableTable`, plus `SchemaFactory` for adapters. DDL lives in a separate server module (`SqlDdlNodes`) and is not part of relational algebra. Costs come from `RelMetadataQuery` (row count, selectivity, cumulative cost), and `EXPLAIN PLAN ... AS JSON` is available. https://calcite.apache.org/docs/algebra.html , https://calcite.apache.org/docs/adapter.html
- **Substrait:** a cross-language protobuf plan format. Logical relations are Read (named table, virtual table, extension table, local files), Filter, Project, Join, Aggregate, Sort, Fetch, Set, Cross and Extension{Single,Multi,Leaf}. Function signatures are declared in YAML extension files referenced by URI/URN with anchors. **WriteRel** (insert, delete, update and CTAS, with `create_mode`) and **DdlRel** (`object`: TABLE or VIEW; `op`: CREATE, CREATE_OR_REPLACE, ALTER, DROP, DROP_IF_EXIST; `table_schema`, `table_defaults`, `view_definition`) exist but are much less mature and cover tables and views only, not indexes or materialized views. Advanced extensions (`AdvancedExtension` with optimization/enhancement Any messages) carry engine-specific hints. https://substrait.io/ , https://docs.rs/substrait-prost/0.87.0/substrait_prost/struct.DdlRel.html , https://docs.rs/substrait-prost/0.98.0/substrait_prost/struct.WriteRel.html , https://github.com/substrait-io/substrait/pull/252
- **DataFusion:** `LogicalPlanBuilder::scan(...).filter(col("a").gt(lit(1)))?.project(...)?.aggregate(...)?.build()`. The `LogicalPlan` enum includes `Ddl(DdlStatement::CreateExternalTable | CreateMemoryTable | CreateView | CreateCatalogSchema | DropTable | DropView | CreateIndex | CreateFunction ...)` and `Dml(DmlStatement{ op: Insert|Update|Delete|Ctas })`, so DDL is a plan node next to the queries. `CreateExternalTable` carries location, file type and options, and `TableProvider` handles external tables with `supports_filters_pushdown`. Extension points: `UserDefinedLogicalNode`, `OptimizerRule`, `AnalyzerRule`, `ExtensionPlanner`. There are Substrait producer and consumer crates, and the proto crate gives plans as protobuf. https://docs.rs/datafusion/latest/datafusion/logical_expr/struct.LogicalPlanBuilder.html , https://docs.rs/datafusion-expr/latest/datafusion_expr/logical_plan/enum.DdlStatement.html
- **Spark Catalog API:** `spark.catalog.listTables/listColumns/tableExists/createTable(name, path, source, schema, options)/cacheTable`. Catalog plugins (`TableCatalog` with `createTable(ident, columns, partitions, properties)` and `alterTable(ident, TableChange...)`) take a typed `TableChange` list (AddColumn, RenameColumn, UpdateColumnType, DeleteColumn, SetProperty), so ALTER is a list of change values. https://spark.apache.org/docs/latest/api/java/org/apache/spark/sql/connector/catalog/TableChange.html
- **Delta Lake DeltaTable API:** `DeltaTable.forPath(...)`, `.merge(src, cond).whenMatchedUpdate(...).whenNotMatchedInsert(...).execute()`, `.history()`, `.restoreToVersion()`, `.optimize().executeZOrderBy()`, `.vacuum()`, and `DeltaTable.createOrReplace(spark).addColumn(...).partitionedBy(...).property(...).execute()`, which is a DDL builder. Every commit is a JSON action log entry (`metaData`, `add`, `remove`, `protocol`). https://docs.delta.io/latest/delta-utility.html , https://docs.delta.io/latest/delta-batch.html#create-a-table

**Lesson:** DataFusion's single LogicalPlan enum with Ddl, Dml and query variants is the cleanest "everything is a plan" design. Spark's `TableChange[]` is the right shape for ALTER. Substrait is a good interchange target for queries, but its DDL coverage is thin, so smaltts must define its own DDL schema. Map it onto Substrait where possible and use extension relations elsewhere.

## 8. Schema-as-code tooling: Liquibase, Flyway, Atlas

- **Liquibase:** a changelog of changeSets, each made of typed change objects (`createTable`, `addColumn`, `createIndex`, `addForeignKeyConstraint`, `renameColumn`, `createView`, ...) in XML, YAML, JSON or SQL. Changes are database-agnostic and rendered per dialect. Many changes support automatic rollback (createTable inverts to dropTable). Preconditions (`tableExists`, `columnExists`, `sqlCheck`) guard changeSets. `updateSQL` (now `update-sql`) previews without applying. `diff` and `diffChangeLog` compare databases. The DATABASECHANGELOG table records applied ids and checksums. https://docs.liquibase.com/change-types/home.html
- **Flyway:** versioned SQL files (`V1__init.sql`), a `flyway_schema_history` table with checksums, `validate`, `info`, `repair`, undo migrations (Teams edition), and callbacks. It is imperative and keeps the operation log as truth. https://documentation.red-gate.com/fd
- **Atlas (ariga.io):** declarative HCL or SQL desired state, `atlas schema inspect` (catalog to HCL or SQL), `atlas schema diff`, `atlas schema apply` with a dry-run plan and approval prompt, and `atlas migrate diff` to generate versioned migration files from the desired-state diff. `atlas.sum` is a migration directory integrity hash. `atlas migrate lint` runs analyzers for destructive changes, data-dependent changes (adding NOT NULL or UNIQUE), backward incompatibility (renames and drops that break old clients) and lock or table-rewrite risk (per-dialect, for example MySQL ALGORITHM and Postgres CONCURRENTLY). Diff policy options include skip-drop and concurrent index. A Go SDK (`schema.Table`, `schema.Column`, `migrate.Plan{Changes []PlanChange{Cmd, Reverse, Source}}`) exposes the plan as data, with a reversible command per change. https://atlasgo.io/declarative/apply , https://atlasgo.io/versioned/lint , https://atlasgo.io/lint/analyzers , https://pkg.go.dev/ariga.io/atlas/sql/migrate#Plan

**Lesson:** The industry has converged on a hybrid. Desired state is authored declaratively, a diff engine produces a reviewable, linted, versioned operation plan, and the applied history is recorded with checksums. Atlas's `migrate.Plan` (each change with its reverse plus diagnostics) is a good model.

## Lessons for a DDL-first, plan-first API (smaltts)

1. **Use both an object model and an operation log, with clear roles.** The *catalog* is an object model (Table, Column, Index, View, MaterializedView, ExternalTable, Connection, Plugin): immutable, typed, and JSON-serializable, with stable ids so renames are not mistaken for drops (DacFx refactor log, Postgres OIDs). *Changes* are typed operations (`createTable`, `alterTable{changes: TableChange[]}`, `drop{cascade|restrict}`), modeled on Spark `TableChange` and Liquibase change types. Never store DDL as text the engine must re-parse (SQLite).
2. **Desired state, diff, plan, apply.** Provide `diff(currentCatalog, desiredCatalog) -> MigrationPlan` (DacFx, Atlas, DBMS_METADATA_DIFF). A plan is a value: an ordered list of steps, each with the op, its inverse when one exists, the dependency edges that forced its order (pg_depend, SMO DependencyWalker), and diagnostics. `apply(plan)` is separate. A dry run means "build plan, render, do not execute" (SMO CaptureSql, Liquibase update-sql, gh-ost --dry-run).
3. **Classify every operation's cost and risk in the plan.** Classes would be `metadataOnly | instant | rebuildsIndex | rewritesTable | blocking`, plus `dataLoss: none|possible|certain` (MySQL ALGORITHM, DacFx alerts, Oracle ALTER_XML safe/lossy, Atlas analyzers, Postgres table_rewrite). Let callers require a class, as in `apply(plan, {require: "instant", blockOnDataLoss: true})`, and fail instead of silently degrading.
4. **Lint as a first-class pass over plans** (Atlas migrate lint, DacFx code analysis): destructive drops, adding NOT NULL without a default, a narrowing type change, a unique index on existing data, a materialized view depending on a dropped column. Return structured diagnostics with codes and do not throw exceptions.
5. **Long or rewriting changes are jobs.** Follow DBMS_REDEFINITION, gh-ost and Data Pump: precheck, start, sync/progress, cut-over, abort, resumable with status. In a browser engine this matters for rebuilding large OPFS-backed tables without blocking the main thread.
6. **Generate DDL from the catalog and round-trip it.** `catalog.introspect()` returns the object model, and `render(obj, dialect?)` / `toSQL()` emits text for humans (GET_DDL, SMO Script(), DuckDB `sql` column, Atlas inspect). Guarantee that `introspect -> desired -> diff` yields an empty plan. Provide a normalized comparison form (Oracle SXML) so defaults and ordering do not cause spurious diffs.
7. **Expose the query side as a lazy relational builder** (Calcite RelBuilder, DataFusion LogicalPlanBuilder, DuckDB relations) that produces the engine's plan data directly. Every relation should support `.explain()`, `.toPlan()` (JSON), `.toSQL()` and sinks (`.insertInto`, `.createTableAs`, `.createMaterializedView`). Views and materialized views should take a builder plan, not a SQL string.
8. **Plans with costs as structured JSON** (Postgres FORMAT JSON, showplan XSD, DBMS_XPLAN): estimated rows, width and cost per node, and actuals after execution. Publish a versioned schema for it. Consider SPM-style "pin this plan" and exportable statistics (DBMS_STATS) so ETL plans stay reproducible.
9. **One plan union for DDL, DML and queries** (DataFusion `LogicalPlan::{Ddl, Dml, ...}`). Batch them into a single transactional plan, and keep Substrait compatibility at the boundary (map queries and Write/Ddl where possible, and use extension relations for indexes and materialized views, which Substrait lacks).
10. **Split external data into Connection, credential and Table** (Postgres SERVER/USER MAPPING/FOREIGN TABLE, DuckDB ATTACH+SECRET). Plugins should implement a pushdown negotiation with costs (SQLite xBestIndex, FDW GetForeignPaths, DataFusion supports_filters_pushdown), not just a scan callback.
11. **Plugins should be versioned catalog objects** with declared functions, types, operators and their upgrade path (Postgres CREATE EXTENSION scripts, Substrait YAML extension URIs). Plans reference functions by plugin, version and name so they stay portable.
12. **Bulk and ETL paths should bypass per-row ops:** an appender or columnar batch insert (DuckDB Appender, COPY, SqlBulkCopy), Arrow-shaped batches, and change capture as data (SQLite changesets, logical decoding, Delta's action log) for incremental pipelines and materialized-view refresh.
13. **Keep the history in the database:** a `migrations` system table with plan hash and checksum (Flyway, Liquibase, atlas.sum) so tools can detect drift (`catalog != applied history`).
